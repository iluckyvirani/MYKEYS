1. ROLES IN THE SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A single User account can hold MULTIPLE roles simultaneously.

  Role      String Value   Who Has It
  ────────  ─────────────  ──────────────────────────────────────────────────
  USER      "USER"         Regular tenant / buyer / renter
  OWNER     "OWNER"        Property owner / landlord
  SERVICE   "SERVICE"      Service professional (plumber, cleaner, etc.)
  ADMIN     "ADMIN"        Platform administrator

Roles are stored in the UserRoleAssignment table (userId + role, unique pair).
The JWT token carries ONE active role (the role the user is currently using).
Users switch role context by logging into a different dashboard view,
which re-issues a new token for that role.

  Body    : { firstName, lastName, email, password, role }

  Body    : { email, password }
  Returns : { user, accessToken, refreshToken, roles[] }

            The token is issued for the chosen role.

FORGOT PASSWORD
  Page    : /forgot-password
  API     : POST /api/auth/forgot-password  →  sends reset email
            POST /api/auth/reset-password   →  sets new password with token

PROFILE UPDATE
  API     : PATCH /api/auth/profile
  Body    : { firstName, lastName, phone, city, state, address, ... }
  Avatar  : POST /api/upload { image: base64, folder: "mykeys/avatars" }
            Returns Cloudinary URL → then PATCH /api/auth/profile { avatar: url }

3. SERVICE PROVIDER REGISTRATION (BECOME A PROVIDER)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Any logged-in USER or OWNER can become a service provider.

REGISTRATION PAGE
  URL   : /services/register
  File  : src/app/services/register/page.tsx
  Form  : src/components/services/ServiceRegistrationForm.tsx

WHAT THE FORM COLLECTS
  - Bio / About yourself
  - Service Category (dropdown from GET /api/services/categories)
  - Service Areas (e.g. "London", "Manchester")
  - Instant Booking: Yes / No
  - Instant Booking Price (£)  — if instant is enabled

HOW IT SUBMITS
  POST /api/users/become-service
  File : src/app/api/users/become-service/route.ts

  Request Headers : Authorization: Bearer <accessToken>
  Body:
  {
    "bio": "Expert plumber with 10 years experience",
    "category": "<ServiceCategoryInfo.id>",   ← UUID of the category
    "subcategories": [],
    "serviceAreas": ["London", "Croydon"],
    "specializations": [],
    "certifications": [],
    "instantBookingEnabled": true,
    "instantBookingPrice": 25
  }

WHAT HAPPENS ON THE BACKEND
  1. Verifies the JWT token.
  2. Checks the user does NOT already have the SERVICE role.
  3. Creates a UserRoleAssignment record: { userId, role: "SERVICE" }
  4. Creates a ServiceProvider record linked to the user.
  5. Issues NEW tokens that include the SERVICE role.
  6. Returns { user, accessToken, refreshToken }

WHAT HAPPENS ON THE FRONTEND
  1. Replaces localStorage accessToken + refreshToken with the new ones.
  2. Redirects to /service/dashboard.

AFTER REGISTRATION — PROVIDER COMPLETES PROFILE
  They can update: bio, service areas, specializations, instant booking price.
  They upload verification documents (SERVICE_CERTIFICATE, SERVICE_LICENSE, etc.)
  Documents are reviewed by admin → admin sets documentVerified = true.

7. BOOKING A SERVICE (BOOKING MODAL FLOW)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The booking modal collects the following in order:

  1. Provider summary (photo, rating, service areas) — read-only
  2. Selected service card (name, price) — read-only
  3. Instant Service toggle (if provider offers it, adds instant fee)
  4. Schedule (hidden when instant is selected):
       - Preferred Date (date picker, today or future)
       - Preferred Time Slot (clickable pills):
           8:00 AM  10:00 AM  12:00 PM  2:00 PM  4:00 PM  6:00 PM  8:00 PM
  5. Service Address (see Section 8)
  6. Additional Notes (optional textarea)
  7. Price Breakdown:
       Base service fee       £XX
       Instant add-on fee     £XX  (if selected)
       Tax (10%)              £XX
       ─────────────────────────
       Total                  £XX
  8. [Cancel]  [Confirm Booking]

VALIDATION
  - If NOT instant: date AND time slot are both required
  - houseNo, street, city, postcode — all required (landmark optional)

BOOKING API CALL
  POST /api/services/book
  Headers: Authorization: Bearer <accessToken>
  Body:
  {
    "providerId"       : "<ServiceProvider.id>",
    "serviceListingId" : "<ServiceListing.id>",
    "service"          : "Standard Boiler Service",
    "category"         : "<ServiceCategoryInfo.id>",
    "bookingType"      : "scheduled" | "instant",
    "description"      : "User notes",
    "scheduledDate"    : "2026-05-10",
    "scheduledTime"    : "10:00 AM",
    "location"         : "12A, Baker Street, near Tesco, London SW1A 1AA (Home)",
    "totalAmount"      : 110
  }

PRICE FORMULA
  subtotal    = basePrice + instantFee
  tax         = subtotal × 0.10
  total       = Math.round(subtotal + tax)   (min 1 if free service)

SUCCESS
  Toast "Booking confirmed!" → redirect to /user/dashboard/service-bookings

9. PROVIDER RECEIVES A BOOKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When booking is created (status = PENDING):
  1. Notification created for provider.
  2. Provider sees it in /service/dashboard/bookings.
  3. Provider actions:
       CONFIRM  → PATCH /api/service/bookings/:id { status: "CONFIRMED" }
       REJECT   → PATCH /api/service/bookings/:id { status: "CANCELLED" }  (notifies user)
  4. When work starts:
       Mark IN_PROGRESS
  5. When work done:
       Mark COMPLETED → provider.completedBookings++ → notify user to review

10. BOOKING STATUS LIFECYCLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ServiceBookingStatus:
  PENDING      Booking created, waiting for provider
  CONFIRMED    Provider accepted
  IN_PROGRESS  Work started
  COMPLETED    Work done — trigger payment
  CANCELLED    Provider rejected OR user cancelled

ServicePaymentStatus:
  PENDING      Not yet paid
  COMPLETED    Payment received
  FAILED       Payment attempt failed
  REFUNDED     Refund issued (for cancellations)

Timeline:
  [User creates booking]  → status=PENDING,  paymentStatus=PENDING
  [Provider confirms]     → status=CONFIRMED
  [Work starts]           → status=IN_PROGRESS
  [Work done]             → status=COMPLETED → trigger Razorpay payment
  [Payment done]          → paymentStatus=COMPLETED
  [If cancelled]          → status=CANCELLED → optional refund

11. PAYMENT FLOW (RAZORPAY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Gateway: Razorpay  |  Currency: GBP  |  Model: Pay-after-service (or upfront)

STEP 1 — CREATE ORDER (server-side)
  API  : POST /api/payments
  Body : { bookingId, amount, currency: "GBP" }
  Returns: { razorpayOrderId, amount, currency, key }

STEP 2 — OPEN CHECKOUT (browser)
  Component: src/components/RazorpayPaymentModal.tsx
  Razorpay modal opens → user enters card / UPI / net banking.
  On success, Razorpay returns:
    { razorpay_order_id, razorpay_payment_id, razorpay_signature }

STEP 3 — VERIFY PAYMENT (server-side HMAC check)
  API  : POST /api/payments/:id/verify
  Body : { razorpayOrderId, razorpayPaymentId, razorpaySignature }
  Backend:
    - Computes HMAC-SHA256(orderId + "|" + paymentId, RAZORPAY_KEY_SECRET)
    - Compares with razorpaySignature
    - If match → Payment.status = COMPLETED → Booking.paymentStatus updated
    - If mismatch → 400 PAYMENT_VERIFICATION_FAILED

STEP 4 — POST-PAYMENT
  - Notification to user: "Payment confirmed"
  - Notification to provider: "Payment received for booking #XYZ"
  - provider.totalEarnings updated
  - ServiceBooking.paymentStatus = COMPLETED, paidAmount = totalAmount

ServiceBooking payment fields:
  paymentStatus   ServicePaymentStatus  @default(PENDING)
  totalAmount     Float                 stored at booking creation
  paidAmount      Float                 @default(0)  updated on payment

12. REVIEWS AFTER COMPLETION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

After booking = COMPLETED, user can submit a review.

  POST /api/services/providers/:providerId/reviews
  Body : { bookingId, rating (1–5), comment }

Effects:
  - ServiceReview record created
  - provider.rating recalculated (weighted average)
  - provider.totalReviews incremented
  - Review visible in:
      /service/dashboard/reviews  (provider sees all their reviews)
      ServiceReviewsModal         (public, shown when user clicks "Reviews" on card)

A user signs up at /signup (role: USER). To offer services, they visit
/services/register, fill in their bio, category, service areas, and optional
instant-booking price. POST /api/users/become-service adds the SERVICE role
and creates a ServiceProvider record — the new JWT token now includes the
SERVICE role. The provider goes to /service/dashboard/services and creates
ServiceListing cards (name, price, description, image). Meanwhile, a regular
user visits /user/dashboard/services, picks a category from the admin-managed
list, picks a provider (sees rating, location, Get Directions link), picks a
listing, and clicks "Book this Service". The booking modal collects a time
slot (clickable pills: 8 AM–8 PM), and a full structured address (house
number, street, optional landmark, city, postcode) — all optionally
auto-filled by clicking "Use Current Location" which uses the browser GPS and
OpenStreetMap reverse geocoding. POST /api/services/book saves a
ServiceBooking with status=PENDING. The provider sees it in their dashboard,
confirms it (CONFIRMED), marks it in-progress (IN_PROGRESS), and marks it
done (COMPLETED). After completion, payment is collected via Razorpay: a
server-side order is created, the user completes checkout in the Razorpay
modal, and the HMAC signature is verified server-side before marking
paymentStatus=COMPLETED and updating the provider's earnings. The user then
leaves a 1–5 star review, which updates the provider's denormalized rating
for future bookings. Admins oversee all bookings, categories, and document
verification from the admin panel.

# 📘 Property Rent & Sale Platform

**Product Requirement Document (PRD)**

---

## 1. Introduction

This project is a **Property Rent & Sale Platform** that allows users to:

* Book properties for **short-term stays** (night-based)
* Rent properties for **long-term duration**
* Buy or sell properties
* Contact property owners through a **secure enquiry system**
* Promote properties for **faster rent or sale**

The platform supports both **users (customers)** and **property owners**, with multiple monetization options.

---

## 2. Objectives

* Provide a simple and trustworthy platform for property renting and selling
* Avoid direct exposure of owner contact details
* Offer premium listing and fast-selling options
* Support both **self-listing** and **assisted listing**
* Generate revenue through packages and promotions

---

## 3. Property Categories

### 3.1 Short-Term Rent (Night-Based Booking)

**Description:**

* Properties can be booked for a short duration (e.g., 1–30 nights)
* Pricing is calculated per night

**Example:**

* Price per night: ₹2,000
* Booking duration: 2 nights
* Total price: ₹4,000

**Key Features:**

* Check-in & check-out date selection
* Night-based price calculation
* Availability calendar
* Booking confirmation
* Optional online payment

---

### 3.2 Long-Term Rent

**Description:**

* Monthly rental properties
* Suitable for families, students, offices, etc.

**Key Features:**

* Monthly rent display
* Security deposit information
* Minimum stay duration
* Enquiry-based contact (no direct phone number)

---

### 3.3 Property Sale

**Description:**

* Property listed for selling
* Buyer sends enquiry to owner

**Key Features:**

* Fixed selling price
* Property details & media
* Secure enquiry system
* Featured promotion option

---

## 4. Property Listing Packages (Owner Side)

### 4.1 Package 1 – Basic / Self Listing

**Features:**

* Owner lists property on their own
* Manual image upload
* Basic property details
* Normal visibility in listing

**Target Users:**

* Budget-conscious owners
* Owners who manage listings themselves

---

### 4.2 Package 2 – Assisted Listing (Professional)

**Features:**

* Platform team support
* Professional photography
* Property video creation
* Optimized property description
* Better visibility and trust

**Target Users:**

* Owners who want professional marketing
* High-value properties

---

### 4.3 Package 3 – Featured / Fast Rent or Sale

**Features:**

* Property appears at the **top of listings**
* Featured badge
* Priority visibility on homepage & search results
* Time-based promotion (7 / 15 / 30 days)

**Target Users:**

* Owners who want fast results

---

## 5. User Side Features

### 5.1 Property Browsing

Users can:

* Browse all properties
* Filter by:

  * Rent type (Short-term / Long-term / Sale)
  * Location
  * Price range
  * Property type
* View images, videos, amenities, and map location

---

### 5.2 Enquiry System (Secure Contact)

**Important Rule:**
Owner phone number is **not visible publicly**

**Enquiry Flow:**

1. User clicks **“Enquiry Now”**

2. Form opens with:

   * Name
   * Mobile number
   * Message (optional)

3. If user is logged in:

   * Name & mobile auto-filled
   * Enquiry sent instantly to owner

4. Owner receives enquiry via:

   * Dashboard
   * Email / notification (optional)

---

### 5.3 Short-Term Booking Flow

1. Select check-in and check-out dates
2. View total price
3. Confirm booking
4. Payment (optional in MVP)
5. Booking confirmation

---

Owners can:

* Add, edit, and delete properties
* Choose or upgrade listing packages
* Upload images and videos
* View enquiries
* Track featured listing duration

### 6.2 Enquiry Management

Owners can:

* View user contact details

* Mark enquiry status:

### 6.3 Promotion Management

Owners can:

* Promote property for fast rent/sale

* Monitor views & enquiries
